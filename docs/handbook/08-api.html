自由文字搜尋(q,ADR-021)。GET /entries 可帶 ?q=,以空白切成多個詞、全部 AND 比對該內容型別每一筆的抽出純文字(string/text/richtext 欄位,component / dynamic zone 子欄位遞迴一層;richtext 比對的是使用者看到的文字,不是區塊 JSON),可以跟 filter 同時用。上限 200 字元,超過回 422 CONTENT_SEARCH_QUERY_TOO_LONG。管理端比對的是工作副本,交付面(見 8.6)比對已發布快照。

展開關聯(populate,ADR-006 Amendment 6、7 與 8)。列表與單筆都能帶 ?populate=author&populate=tags(可重複,值內也可用逗號),展開關聯欄位。值可以用 . 接到最深 3 段(author、author.avatar、author.avatar.owner),第二段起是被展開實體自己的關聯欄位——超過 3 段回 400 CONTENT_POPULATE_TOO_DEEP。結果放在與 data 同層的 related,而巢狀的每一層也是同一個形狀:author.avatar 的頭像掛在 related.author.related.avatar,不是攤平的路徑鍵——只認得單層 related 的舊客戶端,沿它已經懂的鍵往下走一層就讀得到。data 裡的關聯欄位仍然是 id——同一個欄位的 JSON 型別不會因為帶不帶參數而變,沒帶 populate 的回應逐位元組不變。基數跟著 schema:單值給物件或 null,多值給陣列(空的給 []),順序與 data 裡的 id 一致。一個指回自己路徑上某筆實體的關聯(例如 author.mentor.mentor 且 mentor 又指回同一筆 author)會照常渲染那筆實體,但不會再展開進它自己的 related——深度預算沒花完也一樣,擋的是環,不是長度。

管理面展開的是工作副本,不是已發布快照:被展開的實體就是你直接 GET 那一筆會拿到的東西——admin 形狀(data 是工作副本、旁邊帶 published_data 與 has_unpublished_changes)、套目標型別自己的欄位權限,巢狀每一層都一樣。從沒發布過的目標照樣展開(status 就是 draft),因為管理面看的本來就是「即將發布的那一份」;已刪除或別租戶的 id 則是單值 null、多值略過——鍵一定在,「問了但沒有」與「沒問」是不同的答案。目標型別的 read_roles 照樣要過(403),而且每一段各自要過——母體型別可讀不代表它關聯到的型別跟著可讀;目標型別若把你的角色限制成「只看自己建的」,同事的那一列在 related 裡就不會出現,這條規矩同樣跟著下到巢狀的每一層。fields 只作用於母體;整個請求(所有層級加總、去重後)超過 500 個關聯目標回 400 CONTENT_POPULATE_TOO_MANY——單一層沒超過不保證整體沒超過。錯誤碼與交付面完全相同(見 8.6)。預覽憑證不能用:它只指名一筆,回 403 CONTENT_POPULATE_PREVIEW_UNSUPPORTED。

排程發布 / 排程下架(ADR-017)。POST .../schedule 的 body 是 {"action": "publish"|"unpublish", "run_at": "<RFC3339>"},成功回 201。排 publish 時會把工作副本現在的 version 釘住:之後只要有人改了工作副本,這筆排程就作廢(狀態變 stale),不會自動改期、也不會改發新內容——上線的永遠是某個人看過並核准的那一份。排 unpublish 不受編輯影響:下架撤的是已上線的快照,改工作副本沒有改變對外的內容,所以排好的下架照樣到點執行。作廢時會寫一筆 entry.schedule.stale 活動記錄(actor 是那次編輯的人,details 帶 schedule_id / pinned_version / entry_version),但沒有通知——要主動看。手動 publish / unpublish 會讓待執行的排程變 superseded,刪除 entry 會一併刪掉排程。DELETE .../schedule 取消(204),GET .../schedule 回最近一筆(任何狀態;沒有就 404)。一個 entry 同時只能有一筆待執行的排程,要改時間就先取消再排。管理端讀 entry 時,若有待執行(pending)或已作廢(stale)的排程會多帶一個 schedule 欄位——stale 也帶,是因為它是「要人重排」的待辦,不該從畫面上默默消失;done / cancelled / superseded / failed 不帶,那些去 GET .../schedule 問。單筆 GET 與清單(GET /entries)一致帶這個欄位——清單一次查完整頁的排程,不逐列查。對外交付面永遠看不到它。

實際執行由背景 worker 輪詢,精度等於輪詢間隔(SCHEDULE_POLL_INTERVAL,預設 30s),所以排 08:00 會在 08:00 之後的一個輪詢週期內生效。執行失敗不重試,排程標成 failed 並留下原因,活動記錄裡那筆 publish / unpublish 的動作者是當初排程的人,另帶「經由排程」的標記。

排程相關的錯誤碼:

錯誤碼狀態意思
CONTENT_SCHEDULE_ACTION_INVALID422action 不是 publish / unpublish
CONTENT_SCHEDULE_TIME_INVALID422run_at 不是 RFC3339、不在未來,或超過一年
CONTENT_SCHEDULE_EXISTS409已經有一筆待執行的排程(details 帶它的 run_at)
CONTENT_SCHEDULE_NOT_FOUND404沒有排程可取消 / 可讀
CONTENT_SCHEDULE_NOOP422這筆排程什麼都不會改(例如對草稿排下架)

發布修訂版與復原(ADR-018)。每一次上線——人按的、排程放的都算——會留下一版快照,每個 entry 保留最新 20 版,更舊的會被真的刪掉(不是隱藏起來)。下架不留版,因為下架沒有新的上線可記。編號 revision_no 是每個 entry 各自從 1 開始的序號,不是 entry 的 version——後者每存一次草稿就會動,連續兩次上線很可能是 v4 和 v19。保留窗口滿了之後號碼會從比 1 大的數字開始,但窗口內是連號的。

GET .../revisions 回發布史,新到舊,不帶內容(revision_no / version / published_at / published_by / via / via_schedule_id)——不帶不只是為了輕,列表是拿來瀏覽的,把每一版的內容塞進來等於繞過欄位層權限。從沒發布過的 entry 回 [] 而不是 404。GET .../revisions/{no} 才帶 data,並且照讀者的欄位權限遮罩。GET .../revisions/{no}/diff 比的是那一版 vs 現在的工作副本(不是 vs 已上線的快照),因為它要回答的問題是「按下復原會改掉什麼」;回應帶 revision_data / data / changed_keys,讀不到的欄位會被遮掉但仍以 has_hidden_changes 誠實說「這裡也有東西變了」。

POST .../restore 的 body 是 {"revision_no": N},可帶 If-Match。它只寫回工作副本,不發布:status、已上線的快照、published_at 一格都不動,公開站看到的東西跟按之前完全一樣;要把復原後的草稿放上線,是另一個獨立動作、另一道 content:publish 閘門。復原是整份取代不是合併——發布之後才加的欄位會被拿掉,否則結果既不是舊文件也不是新文件。version 會前進,所以釘在舊版本上的待執行 publish 排程會照 ADR-017 的規則變 stale。回應是 {"entry": {...}, "restored_from": {"revision_no", "published_at", "dropped_keys"}};dropped_keys 列出那一版有、但現行內容型別已經不再定義的欄位——這些值無處可放,會被丟掉並具名回報(也會寫進活動記錄),而不是靜靜消失。反過來,發布之後新增的必填欄位、收緊的約束、被別人佔走的唯一值,都落回既有的驗證(422 / 409),復原不為它們另設錯誤碼。復原會寫一筆 entry.restore 活動記錄,details 帶 revision_no / 來源的 published_at / dropped_keys。

欄位層權限照舊生效,但守的是「值真的會變」的欄位:把一個你寫不動的欄位的相同值放回去不算對它的寫入(儲存前後那一格讀起來一樣),所以受限角色不會因為文件裡有受限欄位就永遠復原不了;真的要搬動受限欄位的復原——覆蓋它或把它整個拿掉——照樣 403。對外交付面與預覽面看不到這四支端點(403,而且它們的回應裡不會出現任何修訂版的痕跡);agent 憑證也一律 403,而且擋它的是伺服器側的規則,不是「MCP 沒有提供這個工具」。

錯誤碼狀態意思

欄位除了 type / required / multiple / enum_values,還能帶值層約束:unique(同一 locale 內,工作副本與已發布快照都算)、format: "slug"、pattern(RE2,整串錨定)、min / max(字串是字元數,數字是值)。寫入不符回 422 CONTENT_FIELD_CONSTRAINT_VIOLATED,撞到別人的唯一值回 409 CONTENT_FIELD_VALUE_TAKEN。PATCH 欄位時放寬直接過,收緊會先掃既有資料,不符就 409 附筆數——與 required 同一套規則(ADR-007 Amendment 1)。

可重用元件(ADR-020)。「SEO 區塊」這種總是一起出現的幾個欄位,定義一次成元件(POST /components,帶 name 與 fields[]),再讓型別欄位以 {"type":"component","component":"seo"} 引用;multiple: true 就是一個列表。值內嵌在 entry 裡:單值是物件、多值是物件陣列(最多 100 個),子欄位的 required 與各型別驗證照常生效,錯誤以 meta.title 這種路徑命名。元件本身與子欄位不能當過濾、排序、populate 的鍵,子欄位也不能帶 unique / read_roles / write_roles——權限掛在引用欄位上,整個值一起藏。改一個元件,每個引用它的型別同時跟著變:加 required 子欄位、收緊約束時任一 entry 的任一 item 不符就 409 附筆數;改名與刪除子欄位會在同一個交易裡改寫每個引用型別的每筆 entry(工作副本與已發布快照都改);仍被引用的元件刪不掉(409 CONTENT_COMPONENT_IN_USE,回應列出 used_by)。GET /components/{name} 回子欄位與 used_by;型別 DTO 裡的引用欄位只帶 component 名稱,不內嵌子欄位。schema 產物多一段頂層 components[],排在 types 之前;沒有元件的租戶匯出的位元組不變。

Dynamic zone(ADR-020 Amendment 1)。頁面組裝這種「hero、圖文、CTA 任意排列」的需求,多值 component 表達不了——多值只能重複同一個元件。宣告 {"type":"dynamiczone","components":["hero","cta"]},值恆為陣列(最多 100 個),每個 item 是物件、帶一個 "__component":"hero" 指名自己是哪個元件,其餘 key 就是該元件的子欄位;驗證與 component item 走同一條路,錯誤路徑一樣是 zone.headline 加 item 索引;item 沒帶判別鍵是 422 CONTENT_ZONE_COMPONENT_MISSING,帶了但不在清單裡是 422 CONTENT_ZONE_COMPONENT_NOT_ALLOWED(回應的 allowed 就是那份清單)。multiple 對 zone 是 422(zone 本身就是清單),required 表示至少一個 item。允許清單可以改,兩個方向不對稱:加名字一律放行(名字要存在),拿掉名字時只要還有 entry 在該欄位的工作副本或已發布快照裡持有該元件的 item,就 409 CONTENT_ZONE_COMPONENT_IN_USE 附筆數——清單順序是編輯器 block 選單的順序,保留不排序。因為清單存的是名稱,元件改名成了一次資料遷移:POST /components/{name}/rename 在同一個交易裡改寫每個 zone 兩份 copy 的 __component、就地換掉每個允許清單、再改定義(revision 不改寫)。仍被任何 zone 的允許清單指名的元件刪不掉(同樣是 409 CONTENT_COMPONENT_IN_USE)。zone 與它的 item 同樣不能當過濾、排序、unique、populate 的鍵,zone 也不能當子欄位;delivery 端沒有新東西,值照原樣吐出。

四個 content:schema:* 動詞的破壞性由低到高是 amend → plan → propose → write。只有 write 是 owner / admin 專屬。

成員管理(ADR-022)。GET /tenants/members 回 {"items":[{"user_id","email","role","joined_at"}]},最舊的成員在前,固定上限 200(沒有分頁游標)。PATCH /tenants/members/{user_id} body {"role"}:admin 不能指派或改動 owner 角色(TENANT_CANNOT_ASSIGN_OWNER, 403);不能改自己的角色(TENANT_SELF_ROLE_CHANGE,409——離開租戶是 獨立、目前未提供的功能,不是這支端點的特例);租戶僅剩的 owner 無法被降級 (TENANT_LAST_OWNER,409,由 repository 層鎖強制)。自己對自己降級走的是 TENANT_SELF_ROLE_CHANGE;TENANT_LAST_OWNER 經 HTTP API 唯一可達的 路徑是兩個 owner 併發互降——這時鎖決出唯一贏家,輸的一方拿到 409 TENANT_LAST_OWNER,見 ADR-022 §3/§3b。DELETE /tenants/members/{user_id} 同一套自我操作與 last-owner 規則(TENANT_SELF_REMOVE 409、TENANT_LAST_OWNER 409),移除後會盡力 吊銷該成員在這個租戶的 refresh token,但已核發、尚未過期的 access token 仍在其 TTL(≤15 分鐘)內可用——這是已知、刻意不解的限制。GET /tenants/invites 只列尚未 接受也未撤銷的邀請,回應絕不含原始邀請 token。DELETE /tenants/invites/{id} 撤銷一封待處理邀請;對已撤銷的邀請再次呼叫是成功的空操作(冪等)。被撤銷的邀請之後若被 接受,回 410 INVITE_REVOKED——與既有的「邀請人事後失去 owner/admin 身分」 (INVITE_INVITER_REVOKED)是兩個不同的碼,前者是一次明確的取消,後者是系統偵測到 的附帶後果,見 ADR-022 §4。

站內通知(ADR-023)。四個系統掛點會主動寫入:entry 從「已發布且無未發布變更」 第一次轉為「有未發布變更」時通知租戶 owner/admin(排除觸發者)、排程發布的成功 / 過期作廢 / 失敗三種結果各自通知那次核准排程的人(s.RequestedBy)、webhook 端點被判定死信(重試中的失敗不算)時通知租戶 owner/admin。每筆通知帶 kind(general / schema_proposal / entry_pending_review / schedule_succeeded / schedule_failed / schedule_stale / webhook_dead 七選一)、可為 null 的 link(app 內相對路徑,不是絕對 URL)與可為 null 的 tenant_id ——tenant_id 為 null 表示這筆通知不屬於單一租戶視角過濾,任何租戶上下文下都看得到, 不是「沒有租戶因此誰都看不到」。GET /notifications 與 unread-count 的過濾條件都是 tenant_id = 目前租戶 OR tenant_id IS NULL。PATCH .../{id}/read 對別人的 通知(存在但不屬於呼叫者)與對不存在的 id 回應完全相同的 404,不洩漏 id 是否真實存在。 去抖不靠計時器或去重表,靠後端狀態本身的一次性轉換——細節與已知限制見 ADR-023。

媒體縮圖(ADR-019)。影像上傳 complete 的同一刻就排進縮圖佇列:original 加四個平台固定的 preset ——thumb 320、small 640、medium 1024、large 1920,以寬度為界、永不放大(原圖比 preset 窄的那格會標成 skipped / source_smaller)。JPEG 出 JPEG,PNG / GIF / WebP 一律出 PNG,AVIF 目前整組 skipped(unsupported_format);PDF 這類非影像沒有 variants。縮圖是背景 worker 做的,上傳完成到縮圖可用之間有十幾秒的窗口,這段時間 ?preset= 給的是原圖——頁面不會壞,只是先大圖後小圖。管理端 GET /media/{id} 的 variants 陣列會告訴你每格的 state(pending / done / skipped / failed)、實測的 width_px / height_px、以及失敗時的 error 與 attempts(最多三次,間隔 1 分鐘、5 分鐘)。POST /media/{id}/variants 可以重新排隊,也是舊資產(功能上線前上傳的)唯一長出縮圖的方法——沒有自動回填。re-encode 會丟掉全部 EXIF(GPS、相機資訊都不會出現在縮圖裡),方向資訊在丟掉前已經套到像素上;原圖本身一個位元組都沒動。

跨型別搜尋(/content/search,ADR-021 §3)。q 必填(空字串回 400 CONTENT_SEARCH_QUERY_REQUIRED,跟 /entries 的 q「空字串等於不搜尋」不同),同樣是空白切詞、全部 AND、上限 200 字元。limit 預設 20、上限 50。回應 {"items":[{"id","content_type","locale","status","updated_at","snippet"}]},按 updated_at 新到舊排序,不帶欄位值(跟 /pending-review 一樣,橫跨每個型別沒有單一型別的欄位權限可套)。snippet 是比對到的第一個詞前後各約 60 字的純文字片段,找不到就退回開頭 120 字。跟每型別 q 一樣比對工作副本,即使呼叫者是 viewer 也一樣(這是 staff-only 端點,授權沿用 content:list)。

8.6 對外取用已發佈內容(delivery edge)

前台站台走 :4100,路徑不含 /api 前綴,而且只讀得到已發佈的內容:

GET/v1/{tenant}/{type}/列出已發佈 entry
GET/v1/{tenant}/{type}/{id}取單筆已發佈 entry
GET/v1/{tenant}/media/{id}取已發佈的媒體;可帶 ?preset=thumb|small|medium|large 取縮圖(寬度 320 / 640 / 1024 / 1920,永不放大),縮圖尚未生成或原圖更小時退回原圖,回應裡沒有 variants

列表可帶的參數:locale、limit、cursor(接續上一頁的 next_cursor)、filter(可重複,key:op:value,op 為 eq / neq / gt / gte / lt / lte / in / contains / has / nhas)、sort(key:asc 或 key:desc,單一鍵)、fields(只回這些欄位)、populate(可重複、值內可用逗號,展開關聯欄位)、q(ADR-021,同 8.2 所述的多詞 AND 全文搜尋,原樣轉發到 upstream,比對的是 published_search_text,即已發布快照的抽出文字)。過濾與排序一律對已發布的快照評估,草稿裡的字串探不到、草稿改過的值也不會影響順序。沒有 offset:分頁只走 cursor;不帶 sort 就是固定最新在前。

可排序的鍵就是該內容型別自己定義的欄位,與管理端同一組規則(多值欄位、richtext 與 component 欄位不可排序;component 的子欄位如 meta.title 也不是過濾或排序鍵,ADR-020)。該欄位沒有值的 entry 一律排在最後,升冪降冪都是——否則把方向反過來,第一頁就會塞滿沒填過這個欄位的資料。cursor 與 sort 是綁在一起的:token 記住了它是在哪個排序下發出的,翻頁翻到一半改 sort 會得到 400(CONTENT_CURSOR_INVALID),請丟掉 cursor 從第一頁重翻。這是刻意的:同一個位置在另一個順序裡根本在別的地方,靜默重來只會讓程式無聲地重讀第一頁。

populate 展開關聯,列表與單筆都能用(?populate=author&populate=tags)。值可以用 . 接到最深 3 段(author.avatar、author.avatar.owner),ADR-006 Amendment 8:第二段起是被展開實體自己的關聯欄位,超過 3 段回 400 CONTENT_POPULATE_TOO_DEEP。展開的結果放在與 data 同層的 related,巢狀時每一層同一個形狀——author.avatar 掛在 related.author.related.avatar,不是攤平的路徑鍵。data 裡的關聯欄位仍然是 id ——同一個欄位的型別不會因為帶不帶參數而改變,沒帶 populate 的回應也逐位元組不變。基數跟著 schema:單值欄位給物件或 null,多值欄位給陣列(空的給 []),順序與 data 裡的 id 一致。目標指向草稿、已下架或已刪除的內容不是錯誤:單值給 null、多值直接略過(但鍵一定在,「問了但沒有」與「沒問」是不同的答案)。被展開的實體同樣只給已發布快照、同樣套它自己型別的欄位權限,巢狀的每一層都一樣;fields 只作用於母體。一個指回自己路徑上某筆實體的關聯照常渲染那一筆,但不會再展開進它自己的 related——即使深度預算還沒花完,擋的是環而不是長度。(管理面也能用同一個參數,語法、深度上限、錯誤碼完全相同,展開的是工作副本、看得到從沒發布過的目標——見 8.2。)

populate 的錯誤:CONTENT_POPULATE_FIELD_UNKNOWN(400,型別沒有這個欄位,回應會列出可用的關聯欄位——巢狀路徑任一段皆適用)、CONTENT_POPULATE_NOT_RELATION(400,該段欄位不是關聯,元件與 dynamic zone 欄位一律算在內)、CONTENT_POPULATE_TOO_DEEP(400,超過 3 段)、CONTENT_POPULATE_TOO_MANY(400,整個請求所有層級加總去重後超過 500 個關聯目標——把 limit 調小、少展開幾個欄位,或縮短路徑深度)。多段路徑由左至右解析,第一個失敗的段決定回應。關聯欄位本身或目標型別不可讀時是 403,經 edge 會變成通用的上游錯誤。

需要 delivery 憑證,與 console / agent 憑證是不同的東西。草稿永遠不會從這裡流出去。
