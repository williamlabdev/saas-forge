5. 日常內容操作

5.1 新增一筆內容

  1. 選定一個 content type(GET /api/v1/content/types)。
  2. 建立 entry(POST /api/v1/content/entries),填欄位。存下來時狀態是 draft——此時前台看不到它。
  3. 確認無誤後發佈(POST /api/v1/content/entries/{id}/publish)。狀態轉成 published,delivery edge 立刻讀得到。

要下架:對已發佈的 entry 執行 unpublish,它回到 draft,內容保留。下架不需要發佈權限——止血比放行寬鬆是刻意的設計。

5.2 多語言

同一則內容的各語言版本屬於同一個翻譯群組。在 entry 上可以列出它所有的 locale 版本,彼此獨立編輯與發佈。

5.3 檔案與圖片

file 型別的欄位走物件儲存。上傳分兩步:先向系統要一個上傳位置,傳完再回報完成。取用時系統給的是簽署過的短期 URL,不是永久公開連結。

5.4 預覽

還沒發佈的內容可以產生一條預覽連結,拿給沒有帳號的人看。這是唯一能讓草稿被外部看見的方式,發佈仍然是分開的動作。

5.5 誰改了什麼

在哪看看得到什麼
活動紀錄
GET /content/activity		整個 app 的寫入事件流:誰、什麼時候、動了哪一筆。
單筆 entry 的署名紀錄
GET /content/entries/{id}/attribution		細到欄位層級:這個欄位最後是誰改的,是人改的還是 agent 改的。
agent 改過的欄位一定查得出來每次寫入都記錄行為者類別(human / agent / service),所以「這段文案是 AI 寫的還是人寫的」是可以逐欄位回答的問題,不需要靠猜。

viewer 看不到活動紀錄與發佈佇列(content:activity:read 與 content:review:list)——這兩個是有寫入權的人才看得到的視角。

5.6 Webhook

內容變動要通知外部系統時,在租戶下註冊 webhook。註冊與刪除 webhook 屬於 owner / admin 權限。
