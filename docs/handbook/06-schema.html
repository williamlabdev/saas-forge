6. 改結構:Plan、Apply、提案

改內容是日常,改結構不是。刪一個欄位會讓既有內容裡的那份資料回不來,所以這一章的所有機制都在回答同一個問題:按下去之前,你知不知道會弄丟什麼?

6.1 一律先 Plan

把你想要的目標結構送到 POST /api/v1/content/schema/plan。Plan 不寫入任何東西,它拿你的新結構跟現況比對,把差異拆成一步一步,並替每一步標上等級:

等級意思例子
additive一定可以套用新增欄位、改顯示標籤、新增 content type
guarded要看現有資料才知道行不行把欄位改成必填、換型別——有既有資料就可能擋下
refused結構上不可能,不會執行目標狀態本身矛盾

Plan 同時會告訴你每一步牽動幾筆 entry。這個數字就是「弄丟什麼」的具體答案。要拿現況當起點,先 GET /api/v1/content/schema/export。

Plan 是所有角色都能用的包含 editor(它自己一個權限 content:schema:plan,與寫入分開)。理由很單純:一個看不到 plan 的人,不可能知道自己送出的提案在說什麼。

6.2 接下來能做什麼,取決於你的角色

拿到 plan 之後,同一份變更有兩條出口,你走得了哪一條由角色決定:

角色出口結果
owneradminPOST /content/schema/apply直接執行。
editorPOST /content/schema/proposals送出提案,等 owner / admin 回答。
viewer兩條都不行連 plan 都要 content:schema:plan,viewer 沒有。
給接前端的人的一條版型建議開發用的 console 把這兩條出口做成緊貼 diff 下方的兩顆按鈕(Apply these changes / Send for approval),依角色只出現其中一顆。重點不在按鈕,在於你按下去的東西和你剛剛看的東西要在同一個畫面上——plan 的回應與 apply 的請求是分開的兩次呼叫,中間隔了多遠,是介面自己的選擇。

6.3 提案的一生

  1. editor 送 POST /content/schema/proposals,系統存下這次變更。
  2. owner / admin 在 GET /content/schema/proposals 的待審佇列看到它,附帶有幾項變更、動到哪些型別、以及什麼時候過期。
  3. 審核者取 GET /content/schema/proposals/{id} 展開完整 diff,再送 …/{id}/approve 或 …/{id}/reject。核准即執行,沒有第二道確認。
  4. 提案人查 GET /content/schema/proposals/mine,看得到狀態、到期時間,以及自己視角的 diff。
狀態意思
pending還在等人回答
approved已核准並執行
rejected被駁回,結構沒有變動
expired七天內沒人回答,自動失效;要重送一次
提案有七天壽命過期是伺服器算的,不是客戶端算的——所以不會出現「你的畫面說還沒過期、後端說過期了」這種兩個時鐘的狀況。過期的提案不會自動執行,也不會自動重送。

6.4 提案人看到的 diff 和審核者不同

審核者(…/proposals/{id})看到的是完整範圍的變更計畫。提案人(…/proposals/mine/{id})看到的是他自己權限範圍內的那一份。同一則提案,兩種視角,系統分開保存,不會把審核者的視野漏給提案人——這是兩條端點而不是一條加參數的原因。

少數早期(在此機制上線前)由 agent 送出的提案沒有保留提案人視角,那一列會直說「沒有保留 diff」,而不是拿審核者的版本充數。

6.5 目前的兩個已知限制

一、核准或駁回不會主動通知提案人提案人要自己回頭查 …/proposals/mine。系統目前沒有任何 email 管道,站內通知的觸及範圍和「自己回來看」是一樣的,所以這件事被刻意留著沒做。
二、提案繞不過權限提案是一條審核軌跡,不是一道權限門。直接呼叫 schema/apply 的人,是被權限擋下來的,不是被「沒有提案」擋下來的。
